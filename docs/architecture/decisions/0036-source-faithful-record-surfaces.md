# ADR 0036: Source-Faithful Record Surfaces

Status: proposed for Checkpoint B
Date: 2026-08-24

## Context

Atlas needs coherent record selection, preparation, agent, and encounter views without duplicating canonical semantics across CLI, app DTOs, and frontend code. It also needs to preserve authored content and runtime adjustments without keeping the current creature fallback as a permanent second record.

## Decision

`atlas-app-service` composes three app profiles through generated `atlas-app-model` DTOs:

- `search_compact` for identity, teaser, scan facts, compact traits, and source;
- `record_detail` for complete scan-first awareness, skills, defenses, movement, strikes, spellcasting, abilities, resources/gear, owned content, relationships, and provenance; and
- `encounter_participant` for participant state, final values and explanations, conditions, turn/action state, usable activities, resources, and source-backed capabilities.

All three use one `RecordSurfaceView` outer contract with common record/source metadata, a profile tag, a tagged entity-specific presentation body, and an optional exact encounter bag. `EncounterParticipantView.record_view` carries the participant's projected `RecordSurfaceView`. The creature body represents every zero-or-one semantic domain as an optional named typed object; arrays are reserved for true-many skills, movement modes, resources, spellcasting entries, activities, owned content, and relationships. Genuinely known-empty collections are absent from serialized record/API surfaces and optional in generated TypeScript, while populated collections preserve authored order. A selected creature domain with a missing, null, unsupported, ambiguous, failed, or unsafe canonical root or required nested member uses the optional named `unavailable_domains` sidecar. Each affected domain contains typed causes with source state, affected field, optional component identity, and canonical-field provenance; messages are display-only. The unsafe ordinary value is omitted, but its cause remains distinct from known-empty omission. The sidecar is not a second presentation model, a generic field registry, or an automation limitation, and it exposes no raw source path. Stable profile order and density are contract/app-service composition policy, so there is no `sections[]`, string-key semantic lookup, or `section_order`. Non-creature families return the explicit unavailable presentation boundary.

Encounter runtime composition is a prerequisite contract, not a generic profile implementation. `EncounterRuntimeView` uses named typed fields for zero-or-one semantic areas and typed collections for genuinely repeated domains. It owns current/temporary HP, conditions, action state, final adjusted values, applied/suppressed explanations, and tagged provenance. Runtime activities carry their canonical occurrence traits and associated typed rich content directly. The encounter creature body retains only canonical facts without runtime counterparts: IWR and hardness, AC context without static AC, authored save notes/details without static modifiers, and senses/languages/details without static perception. This gives consumers one composed response without static/runtime duplication, a second fetch, or a client join. Static and runtime spell rows directly own authored embedded spell content resolved through typed occurrence or exact actor-local target associations; claimed documents are removed from general content, repeated occurrences remain independent, and association ambiguity fails affected rows closed. Runtime spellcasting nests canonical entry labels/order/preparation/tradition with final attack/DC/slots and ordered occurrence spells; creature-parent spells remain explicit with content under static and runtime `standalone_spells`, unrelated embedded capability content remains general, and spell rows are absent from generic activities. Each runtime spell row also exposes typed cast availability and its exact spend ownership: prepared slot, spontaneous rank pool, innate occurrence use, focus pool, or stateless at-will. App-service initializes only supported typed canonical current values into durable participant-local state, validates the requested occurrence and spend owner on each cast or restore, and exposes typed unavailable state instead of guessing when current facts or ownership are absent or ambiguous. Encounter resource rows remain present when a typed runtime consumer exists even if current state is unavailable, or when supported participant-local current state exists without a consumer; an unattached provenance-only resource remains available on the static record but is omitted from encounter runtime. A separate typed destructive confirmation invokes the atomic generic participant reset; availability is false for legacy rows without a creation baseline, while successful results enumerate reset and preserved domains. Automatic daily-rest and refocus behavior remains out of scope. `StatBlockView`, `StatValueView`, generic section/value arrays, target-string semantic lookup, and consumer-side owner joins are not compatibility surfaces.

The runtime DTO exposes only user-relevant incomplete automation as stable typed limitation codes with typed participant, condition, activity, or spellcasting placement targets. Limitation messages are display-only. Projection diagnostics for malformed, duplicate, unsupported, unmapped, raw-path, publication, null, and source-noise facts stay internal to app-service, and missing or unsafe critical data fails closed or leaves the affected typed value unavailable. Raw source and provenance remain separately owned rather than being copied into a generic public note bag.

`atlas-web` remains transport. `web/atlas-ui` uses Ant Design for generic application controls and PF2e-specific components for record/runtime layouts. It renders generated semantics and hosts feature-owned interaction slots; it does not parse Foundry JSON or prose, infer mechanics, or reconcile static and runtime facts. Encounter-profile creature bodies omit canonical mechanics represented by the attached runtime bag, preventing duplicate canonical and final adjusted values in one response while retaining owned content and provenance.

ADR 0023 remains authoritative for CLI JSON. CLI record-bearing commands share one `atlas-record::RecordJson`: a genuinely common flattened base plus a mandatory tagged entity presentation. The first family-specific body is creature and directly exposes typed defenses, awareness, skills, movement, resources, activities, and spellcasting. Detail levels omit unhydrated entity members rather than emitting empty placeholders; empty members remain only for included sections where known-empty is intentional. Rich content remains supplementary. Non-creature families use an explicit registry-bound `unmigrated` boundary only until their H-family plan lands. The earlier additive generic-section direction is superseded; this unreleased contract is replaced directly with no compatibility shim, dual serializer, or feature switch. App DTOs and a parallel CLI semantic model remain forbidden.

The ordinary creature terminal renderer keeps ownership and occurrence locators as placement rules rather than headings: authored content appears under natural record, ability, spell, equipment, Lore, or note labels, and spellcasting uses entry-to-rank hierarchy with distinct ordered rows. `atlas record provenance <canonical-key>` is the separate typed diagnostic surface for full fact provenance, occurrence identities and locators, content ownership, verified edition context, embedded relationships, and exact reference/backlink provenance. Its optional `--json` uses the shared envelope; it does not parse or expose raw source and does not change Full or `--include-raw` semantics.

The CLI and app projections receive the `atlas-record`-owned `RetrievedRecord` aggregate produced by index canonical hydration and preserved by search. Both read creature presentation values exclusively from `RecordBody::Creature`; `AtlasRecord.mechanics` remains a separate sparse projection and is never a recovery path. App-service consumes the complete aggregate for its typed record-surface profiles and passes the complete aggregate to the local CLI.

`RichDocument` remains the once-parsed authored content tree. Record, entity, occurrence, child, content, and section targets remain addressable. The default child embedding policy remains overflow-only. Copied embedded capability prose stays reachable through its owner but is excluded from default ranking to prevent duplicate-result flooding, not because of authorization.

For creature activity presentation, app-service resolves an activity's typed occurrence target and composes its occurrence-owned content with content owned by the exact targeted actor-local entity. The activity exposes those documents once as ordered typed rich-content blocks and general overview/lore excludes them. Association failure is fail-closed for that activity. `atlas-record` owns the structured `RichDocument` projection, including authored paragraph/divider boundaries and a typed Foundry `Check` inline carrying display fallback plus optional statistic and numeric DC; web rendering consumes that DTO without label matching, ID parsing, raw HTML parsing, or a frontend join.

Current CLI/app/UI behavior is unauthenticated but inherits pinned-base default-visible/public-only routing and is not GM-complete. The approved target preserves typed visibility, role, and provenance as metadata while preventing classification-only suppression of useful authored information; no present security boundary is claimed. D2 produces CLI JSON/text and agent behavior, then D3 audits only the available source/artifact/search/CLI/agent surfaces. E3 separately verifies generated app DTOs/composition/transport. F1/F2 produce record and encounter UI, F3 audits the completed browser/static/runtime matrix, Checkpoint E owns human visual approval, and G2 verifies the final staged evidence and cutover residue.

A4 screenshots are diagnostic only. F3 automation runs only after F2 and must pass the complete hashed fixture/viewport/theme/static/runtime matrix, including rejection of classification-only suppression; only Checkpoint E provides human visual approval. Creature fallback removal is forbidden before that approval, and G2 later verifies the complete evidence chain.

## Consequences

Search, CLI, app, and UI can differ in projection shape while deriving from one canonical semantic record. Runtime final values replace duplicate base display values. Non-creature families keep exact H1-H11 ownership and require separate plans and approvals; each plan must include a field-level disposition ledger, fixtures, exact owners/rationales, surface/runtime decisions, validation, and approval path, and H12 rejects missing or generic packages.
